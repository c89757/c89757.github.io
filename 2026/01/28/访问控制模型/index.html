访问控制模型

2026-01-28 other 0 评论

DAC

Discretionary Access Control。自主访问控制模型

允许合法用户以用户或用户组的身份访问策略规定的客体，同时阻止非授权用户访问客体。

实现：权限控制列表（ACL）

​ 每一个客体都配有一个列表，这个列表记录了主体对客体进行何种操作。当系统试图访问客体时，先检查这个列表中是否有关于当前用户的访问权限。ACL 是一种面向资源的访问控制模型，它的机制是围绕资源展开的。

  1. 主体（Subject）属性

    谁在请求？

  2. 客体（Object）属性

    请求什么资源？

如Linux中的文件系统

MAC

Mandatory Access Control。强制访问控制

目标是限制主体或发起者访问或对对象或目标执行某种操作的能力。任何主体对任何对象的任何操作都将根据一组授权规则（也称策略）进行测试，决定操作是否允许。

  • Subject 被赋予一定的安全级别
  • Object 被赋予一定的安全级别
  • Subject 能否访问 Object 由双方的关系安全级别决定，这个判断通常有系统硬性限制.

强制访问控制系统根据主体和客体的敏感标记来决定访问模式，模式包括：

  • 不上读（NRU），主体不可读安全级别高于他的数据；
  • 不下读（NRD），主体不可读安全级别低于他的数据
  • 不上写（NWU），主体不可写安全级别高于他的数据。
  • 不下写（NWD），主体不可写安全级别低于他的数据。

常见的模型：

  • BLP模型：不上读，不下写。即不允许低安全等级的用户读取高安全等级的信息，不允许高敏感度的信息写入低敏感度的区域，禁止信息从高级别流向低级别

  • Biba模型：不下读，不上写。即不允许高安全等级的用户读取低安全等级的信息，不允许低敏感度的信息写入高敏感度的区域。主要为了能保证数据的完整性。

    在实际的应用中主要是避免应用程序修改某些重要的系统程序或系统数据库，这样可以使资源的完整性得到保障。也就是写，只能读上级发给他的命令，不能读他的下级接收到什么

MAC主要适用于军方等安全要求比较高的行业

RBAC

Role Based Access Control。基于角色访问控制

用户 —— 角色 —— 权限

用户拥有角色，基于角色分配权限

  • RBAC0

用户与角色之间，多对多

角色与权限之间，多对多

用户通过分配角色来获取权限

  • RBAC1

在RBAC0基础上增加 角色继承

允许角色继承来自动继承其权限

简化了权限管理工作

  • RBAC2

在 RBAC0 基础上增加 静态/动态职责分离等约束规则。

典型约束包括：

静态职责分离（SSD）：用户不能同时被分配互斥角色（如 “会计” 和 “审计” 不能为同一人）。

动态职责分离（DSD）：用户在同一会话中不能激活互斥角色。

基数约束：角色激活数量限制、权限使用条件等。

增强了安全性，防止权限滥用或利益冲突。

  • RBAC3

RBAC3 = RBAC1 + RBAC2

ABAC

Attribute Based Access Control。基于属性的访问控制

通过动态计算一个或一组属性是否满足某种条件来进行授权判断。可以按需实现不同颗粒度的权限控制

ABAC的访问角色基于以下四类属性：

  1. 主体（Subject）属性
    • 谁在请求？例如：用户角色、部门等。
  2. 客体（Object）属性
    • 请求什么资源？例如：文件密级、数据类型等。
  3. 操作（Action）属性
    • 执行什么操作？例如：读、写、删除、导出等。
  4. 环境（Environment）属性
    • 在什么条件下？例如：时间、地点、网络类型等。

决策逻辑

系统通过预定义的策略（Policy）对这些属性进行逻辑判断。

比如：

允许财务部（subject.department == ‘Finance’）员工在工作时间（9:00–18:00）从公司内网（environment.network == ‘internal’）读取机密级别为‘Confidential’的文档（object.classification == ‘Confidential’）。

优点：灵活度高、控制更加细粒，易于扩展

缺点：复杂度较高
