PostgreSQL是伯克利原始代码的开源后代。它支持 SQL 标准的大部分内容，并提供了许多现代功能：

窗口函数

窗口函数对与当前行以某种方式相关的一组表行执行计算。这与可以使用聚合函数完成的计算类型相当。但是，窗口函数不会像非窗口聚合调用那样导致行分组为单个输出行。

窗口函数调用总是在窗口函数名称和参数之后直接包含一个 OVER 子句。OVER 子句确切地决定了窗口函数如何分割查询行以进行处理。OVER 中的 PARTITION BY 子句将记录分为多个组或分区，这些组或分区共享相同的 PARTITION BY 表达式值

还可以使用 OVER 中的 ORDER BY 来控制窗口函数处理行的顺序

​ 与窗口函数相关的另一个重要概念是：对于每一行，其分区中都有一组行，称为窗口帧。有些窗口函数只作用于窗口帧中的行，而不是整个分区中的行。默认情况下，如果写了 ORDER BY，则窗口帧包括从分区起始行到当前行的所有行，以及根据 ORDER BY 子句与当前行相等的所有后续行。如果省略 ORDER BY，默认窗口帧由分区中的所有记录组成。

生成列

​ 生成列是一种特殊的列，它始终由其他列计算得出。

​ 生成列有两种类型：存储型和虚拟型。存储型生成列在写入（插入或更新）时计算，并像普通列一样占用存储空间。虚拟型生成列不占用存储空间，在读取时计算。因此，虚拟型生成列类似于视图，而存储型生成列类似于物化视图（区别在于它始终自动更新）。PostgreSQL 目前仅支持存储型生成列。

  • 创建虚拟列

关键字STORED用于指定生成列的存储类型

生成的列不能直接写入。在 INSERT 或 UPDATE 命令中，不能为生成列指定值，但可以指定关键字 DEFAULT。

系统列

每个表都包含若干系统隐式定义的系统列。因此，这些列名不能用作用户自定义列的名称

  • tableoid

    此列是包含该行的表的 OID。对于从分区表或继承层次结构中选择数据的查询，如果没有它，很难确定一行数据来自哪个表。tableoid 可以与 pg_class 的 oid 列连接来获取表名。

  • xmin

    此行版本插入事务的标识（事务 ID）。（行版本是行的一个特定状态；每次更新行都会为同一逻辑行创建一个新的行版本。）

  • cmin

    插入事务中的命令标识符（从零开始）。

  • xmax

    删除事务的标识（事务 ID），如果行版本未删除，则此列值为零。在可见行版本中，此列的值可能不为零。这通常表示删除事务尚未提交，或者删除尝试已被回滚。

  • cmax

    删除事务中的命令标识符，或零。

  • ctid

    行版本在其表中的物理位置。主键应用于标识逻辑行。

表分区

分区是指将逻辑上是一个大表的数据存储分割成若干个较小的物理分区。分区可以带来以下几个好处：

  • 在某些情况下，查询性能可以得到显著提升，尤其是在表中大部分访问频繁的行都位于单个分区或少数几个分区中时。分区有效地替代了索引树的上层结构，使得索引中频繁使用的部分更有可能被加载到内存中。
  • 当查询或更新操作访问单个分区的很大一部分时，可以通过对该分区进行顺序扫描而不是使用索引来提高性能，因为顺序扫描需要对整个表进行分散的随机访问读取。
  • 如果分区设计中考虑了使用模式，则可以通过添加或删除分区来完成批量加载和删除。使用 DROP TABLE 删除单个分区或执行 ALTER TABLE DETACH PARTITION 比批量操作要快得多。这些命令还完全避免了批量 DELETE 造成的 VACUUM （数据库清理）开销。
  • 不常用的数据可以迁移到更便宜但速度较慢的存储介质上。

PG内置支持以下几种分区

  • Range Partitioning 范围分区

    表被划分为由关键列或列集定义的 “范围”，分配给不同分区的值范围之间没有重叠。例如，可以按日期范围或特定业务对象的标识符范围进行分区。每个范围的界限可以理解为下端包含，上端不包含。例如，如果一个分区的范围是从 1 到 10，而下一个分区的范围是从 10 到 20，那么值 10 就属于第二个分区，而不属于第一个分区。（左闭右开）

  • List Partitioning 列表分区

    通过明确列出每个分区中出现的键值来对表进行分区。

声明式分区

​ PG允许声明将表划分为多个分区。被划分后的表称为分区表。

​ 分区表本身是一个“虚拟”表，它本身没有存储空间。存储空间属于各个分区，这些分区是与分区表关联的普通表。

​ 每个分区存储由其分区边界定义的数据子集。插入到分区表中的所有行都会根据分区键列的值被路由到相应的分区。如果更新了某行的分区键，并且该行不再满足其原始分区的边界，则该行将被移动到另一个分区。

​ 分区本身可以定义为分区表，从而形成子分区。无法将普通表转换为分区表，反之亦然。但是，可以将现有的普通表或分区表添加为分区表的分区，或者从分区表中删除分区，使其成为独立表

例如：

  1. 要创建一个分区表，根据时间分区
  1. 创建分区。

每个分区的定义必须指定与父分区的分区方法和分区键相对应的边界

在分区表上创建索引。这将自动在每个分区上创建匹配的索引，以后创建或附加的任何分区也将有这样的索引。在分区表上声明的索引或唯一约束是 “虚拟 ”的，这与分区表是 “虚拟 ”的一样：实际数据在各个分区表的子索引中。

声明式分区需要注意的点：

  1. 分区必须与分区表具有完全相同的列集。
  2. 要在分区表上创建唯一键或主键约束，分区键不得包含任何表达式或函数调用，约束列必须包含所有分区键列。存在这种限制是因为构成约束的各个索引只能直接在自己的分区内强制执行唯一性；因此，分区结构本身必须保证不同分区之间不存在重复。

我们常常需要删除存放旧数据的分区，并定期添加新分区来存放新数据。分区最重要的优势之一就在于，它允许我们通过操作分区结构来快速完成这项原本繁琐的任务，而无需实际移动大量数据。

更方便的做法，是先创建新表，然后再将其附加为分区。这样就可以在新数据出现在分区表之前对其进行加载、检查和转换。

此外，ATTACH PARTITION 操作只需要分区表上的 SHARE UPDATE 独占锁，而不是 CREATE TABLE … PARTITION 所需的 ACCESS 独占锁。PARTITION OF 所要求的 ACCESS EXCLUSIVE 锁，因此它对分区表上的并发操作更友好

运行ATTACH PARTITION命令前，建议CHECK在要附加的表上创建一个与预期分区约束相匹配的约束。这样，系统就可以跳过验证隐式分区约束所需的扫描，如果没有该CHECK约束，系统会在锁定该分区的同时扫描表以验证分区约束ACCESS EXCLUSIVE。ATTACH PARTITION 完成后可以删除多余的 CHECK 约束。

如果被附加的表本身是一个分区表，那么它的每个子分区都将被递归锁定和扫描，直到遇到合适的 CHECK 约束或达到叶分区为止

使用继承进行分区

某些情况下，使用继承的方式更灵活

  • 对于声明式分区，分区必须与分区表具有完全相同的列集；而对于表继承，子表可以具有父表中不存在的额外列。
  • 表继承允许多重继承。
  • 声明式分区仅支持范围分区、列表分区和哈希分区，而表继承允许用户以自己选择的方式划分数据。

继承分区注意：

  • 索引和外键约束适用于单个表，而不适用于其继承的子表，因此需要注意一些注意事项。

分区修剪

​ 分区修剪是一种查询优化技术，可以提高声明式分区表的性能

​ 如果没有分区修剪，上述查询会扫描表的每个分区measurement。启用分区修剪后，查询规划器会检查每个分区的定义，并证明该分区无需扫描，因为它不能包含任何满足查询 WHERE 子句的行。当规划器可以证明这一点时，它会从查询计划中排除（修剪）该分区。

分区和约束排除

​ 约束排除是一种类似于分区剪枝的查询优化技术。虽然它主要用于使用传统继承方法实现的分区，但也可以用于其他用途，包括声明式分区。

​ 约束排除的工作原理与分区修剪非常相似，区别在于约束排除使用每个表的CHECK约束（这也是它名称的由来），而分区修剪使用表的分区边界，分区边界仅在声明式分区的情况下存在。另一个区别是，约束排除仅在执行计划时应用。

​ 约束排除使用 CHECK 约束，这使得它比分区修剪慢，有时可以用作一个优点：因为除了其内部分区边界之外，甚至可以在声明式分区表上定义约束，因此约束排除可能能够从查询计划中删除其他分区。
